# BFF 测试故障诊断

诊断先建立可复现证据链。用户只要求诊断时，报告根因和建议，不修改代码。

## 最小反馈回路

1. 明确预期 tag、operation、最终业务请求和前置链路。
2. 复用用户原命令，或构造能复现同一症状的最小命令。
3. 保存错误摘要、Locust 原始产物和必要的响应结构；对 token、账号和个人数据脱敏。
4. 列出少量可证伪假设，每次只改变一个变量。
5. 偶发失败至少做受控复跑或比较同时间窗口的其他请求，再判断是否为代码问题。

若真实环境不可访问，使用单元测试、响应回放、静态资产检查或 catalog 跟踪建立局部证据，并清楚标注未验证边界。

## 从最早偏差分层

| 层级 | 典型症状 | 检查重点 |
| --- | --- | --- |
| 选择与注册 | tag 无 task、目标请求未出现 | catalog、tag filter、registry、导入失败 |
| 运行时配置 | 账号池为空、环境不符 | profile 是否显式加载、URL override 范围 |
| 认证与上下文 | 401/403、租户或设备状态缺失 | 登录 flow、状态写入、切换后的上下文刷新 |
| 测试数据 | 列表为空、对象不存在、一次性数据耗尽 | 数据前置、权限、选择条件和清理策略 |
| GraphQL 契约 | 字段/参数错误、GraphQL errors | Schema 来源、operation、变量、生成器配置 |
| Transport | 超时、连接失败、5xx | 网络、endpoint、header、重试和服务状态 |
| 业务断言 | HTTP 200 但失败 | 业务码、response parser、目标字段 |
| 报告 | 主请求缺失、指标错配或报告误判通过 | catalog 主请求、原始 stats 精确行名、fallback、解析器和模板输入 |

诊断“目标请求未进入报告”时按固定证据方向检查：先读取 catalog 的显式主请求，再在原始 stats 中做精确名称匹配，随后检查 task 实际上报名称，最后才检查 parser 和模板。若 parser 在显式主请求缺失时回退到其他业务行或 `Aggregated`，应判定为报告口径缺陷，不能把回退指标当成目标请求证据。

## 性能回退

- 先确认负载模型、profile、数据规模和版本可比。
- 区分目标请求与 Aggregated 指标，检查错误率、吞吐、分位延迟和饱和迹象。
- 将客户端等待、前置链路、服务端处理和网络波动分开分析。
- 没有可比基线时只描述当前观测，不宣称发生回退。

## 诊断输出

给出根因或当前最强假设、直接证据、受影响范围、已排除项、仍需的信息和最小复现命令。环境、数据与脚本问题要分别标注，不用单元测试通过覆盖真实环境失败，也不用一次真实成功覆盖确定性测试失败。
