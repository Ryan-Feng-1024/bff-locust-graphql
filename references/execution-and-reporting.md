# 冒烟、性能测试与报告

## 先判断运行目的

| 目的 | 推荐入口 |
| --- | --- |
| 代码和注册快速回归 | 项目统一测试脚本或目标 pytest |
| 场景最小可运行性 | 目标 headless/runner 测试 |
| 真实接口验活 | 正式 Locust 单 tag 冒烟 |
| 发布批次冒烟 | 项目 smoke wrapper 与 catalog 分组 |
| 性能结论 | performance wrapper、明确负载模型和阈值 |
| 原始产物定位 | Locust HTML/CSV/JSON 包装入口 |

pytest/headless 可以缩短反馈，但不能替代项目规定的正式 Locust 冒烟或性能口径。

## 执行前

1. 通过项目脚本或 catalog 把用户输入解析为准确 tag，不依赖大小写或命名猜测。
2. 显式选择运行时 profile，确认 endpoint、账号池容量、客户端模式和数据权限。
3. 确认场景执行策略。破坏性、一次性和数据依赖场景不得默认并入 regular smoke。
4. 确认用户数、spawn rate、运行时长、等待模型和输出目录。
5. 检查是否已有 Locust 进程使用同一账号池；共享登录态时串行执行。

若项目未定义冒烟参数，可把 `1` 用户、`1` spawn rate、约 `30s` 作为保守起点，但应明确这是回退值，不是跨项目标准。

## 冒烟判定

- 目标 tag 被加载，catalog 指定的最终业务请求确实出现。
- 登录、预取和准备步骤不能替代主请求成功。
- Locust failure、HTTP 错误、GraphQL errors 与业务失败均为判定依据。
- 短时验活优先使用项目定义的 validity 或一次性模式，不能因此削弱原性能 tag 的持续负载语义。
- 如果仅确认服务可用，不擅自延长为性能或稳定性测试。

## 性能判定

- 使用原始业务场景和项目正式 wait/workload profile，不以 validity 场景形成性能结论。
- 记录 users、spawn rate、运行时间、等待模型、profile、客户端入口和目标环境。
- 依据项目 threshold/tier 评估目标请求，而不是只看 aggregated 行。
- 与基线比较时保持环境、数据规模和负载模型可比；不把网络波动或环境异常直接归因于代码回退。

## 报告边界

- 保留原始 Locust stats、failures、history、HTML/JSON 和运行元数据。
- 报告解析器负责目标行识别、阈值判断、错误分类和缺失产物处理。
- catalog 已显式声明主请求时，原始 stats 中缺少该请求必须判失败。不得回退到其他业务行或 `Aggregated` 后仍用显式主请求名展示并判绿。
- Jinja2 或其他模板只渲染已计算的数据，不在模板中解析 CSV 或实现业务判断。
- 报告失败时先保留产物，再检查目标请求、失败详情、解析问题和评估依据。
- 报告必须反映本次实际 profile、wait model 和客户端入口，不能沿用默认文案造成口径错配。

交付时汇总运行参数、目标请求指标、失败分类、阈值结论和产物位置。真实环境未执行时明确说明原因。
