# 场景新增与更新

## 先定义场景契约

在写代码前确认：业务目标、GraphQL operation、前置链路、最终主请求、客户端范围、数据依赖、是否修改数据、预期执行频率，以及短时验活与持续负载是否语义相同。

目标仓库若有分类指南，先据此确定 tier、smoke stage、category、load profile、execution policy 等字段。字段名和枚举由项目定义，不从参考项目照搬。

## 选择实现基线

1. 找一条认证方式、客户端、分页方式和数据风险最接近的现有场景。
2. 复用它的用户基类、会话状态、GraphQL builder、失败上报和注册方式。
3. 多步骤链路把准备请求与最终业务请求分开；catalog 的主请求应指向业务目标，不指向登录或预取。
4. 对破坏性、一次性、负向契约或强数据依赖场景，使用项目已有的隔离策略，不混入常规全量冒烟。
5. 若持续压测必须反复执行，而短时验活需要限制次数或数据量，保留性能场景语义，并按项目约定增加独立 validity 场景或等价机制。

项目存在 scaffold 时先使用 scaffold，但把生成结果视为待完善的骨架。生成后逐项检查 operation 输入、变量 builder、数据来源、主请求名称、失败上报和测试断言；不得因为脚手架成功退出或 catalog 校验通过就认为场景已完成。先运行 GraphQL drift 确认最小骨架能被判红，再补全契约并验证转绿。

## 实施清单

- 新增或修改 task，并遵守项目命名、tag 和自动注册约定。
- 使用统一状态对象获取认证、租户、设备和业务上下文；值可能为空时先校验并走项目已有的失败或跳过机制。
- 请求变量通过 builder、模板或变量资产构造，不在 task 中嵌入完整 GraphQL 文本。
- 分页、列表选取、上传和多阶段 flow 优先复用公共 helper。
- 失败必须进入 Locust 统计或项目等价的失败通道，GraphQL errors 与业务失败不能被 HTTP 200 掩盖。
- 新增最小 task 单测和项目要求的 headless/runner 场景测试。
- 动态变量来自 session、租户、设备或前置响应时，至少用一个窄单测锁定“上下文值进入 builder/request”的契约。
- 更新 catalog、阈值、workload 和生成文档等项目主数据消费者。
- Python 类型可能为 `None` 或动态结构时明确收窄，不用大范围 ignore 掩盖契约问题。
- 对生成和手工修改的 Python 文件运行项目 formatter/linter；脚手架产物不天然保证符合当前静态规则。

## GraphQL 关联

新增或改变 operation 时，按 [graphql-assets.md](graphql-assets.md) 从当前 server Schema 或项目认可的本地 Schema 生成资产。不要先手写裁剪版本再补字段。

## 完成前自检

- tag 能解析到唯一场景，且注册器确实加载该 task。
- 前置请求失败时不会继续用无效状态调用主请求。
- headless 测试断言目标请求出现且失败数为零，而不是仅断言总请求数或任意前置请求成功。
- catalog 的 operation、资产路径、主请求和执行策略与实现一致。
- 修改场景后，按目标项目要求完成一次正式 Locust 单场景冒烟；环境不可用时明确列为未验证项。
