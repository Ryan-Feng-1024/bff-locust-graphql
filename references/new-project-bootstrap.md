# 空目录与新项目启动

当目标目录为空、不是仓库，或只有零散文件而没有可运行的 BFF 测试框架时，使用本工作流。目标是建立与目标 BFF 契约相符、能离线验证并可安全接入真实环境的最小项目，不是复制一个参考仓库后改名。

## 先区分事实、线索与待确认项

- 用户提供的 GraphQL URL 只确认 endpoint 候选，不能证明认证方式、Header、账号池、租户、设备上下文、业务数据或 Schema 可直接使用。
- 相邻前端、移动端、后端仓库可提供 operation、Header、设备字段和业务链路线索；生成代码和旧文档可能滞后，不能替代 live Schema 与真实响应。
- 参考测试仓库只提供架构候选。比较其认证方式、客户端范围、GraphQL 生成器、报告口径、profile 模型和业务上下文，再决定复用范围。
- 文档、客户端代码、生成类型和 live Schema 冲突时，记录漂移；不要静默选择最方便的一方。

用户要求“先分析”“不要动作”时，只做只读发现并输出建议，不创建目录、初始化 Git、安装依赖、访问真实 BFF 或生成资产。用户随后要求继续时，按已确认范围执行最小下一阶段，不把之前的分析授权扩张为真实写操作或业务 mutation 授权。

## 问答应解决的决策

不要把建置变成冗长问卷。先从用户给出的 URL、相邻产品代码和参考仓库推断可验证事实，仅询问会实质改变项目结构或真实环境风险的事项：

1. **首期目标**：只做契约/冒烟，还是同时包含正式性能测试与报告。
2. **场景边界**：认证验活、只读查询、写操作、上传或删除分别是否纳入；默认先做认证基础设施和只读场景，将有副作用场景隔离。
3. **认证与数据**：profile 名、账号池或 token/OTP/once-token 来源、设备与租户上下文、稳定业务 ID 的来源；秘密不得写入仓库。
4. **参考基线**：是否有指定参考仓库。没有时，选择职责最接近者，并说明复用与不复用的部分。
5. **工程边界**：是否初始化 Git、是否需要 CI、容器或部署配置。这些不是仅因创建测试项目就自动获得的授权。

如果用户尚不能提供真实账号或业务数据，仍可建立离线可验证骨架、示例 profile schema 和数据接口，但不得伪造“真实冒烟已通过”。

## 选择参考项目

候选项目至少比较以下维度：

| 维度 | 选择依据 |
| --- | --- |
| 认证 | anonymous、OTP、once token、第三方登录或既有 session 是否接近 |
| 请求协议 | Header、deviceData、trace、token 与 multipart 方式是否接近 |
| 业务上下文 | 租户、服务号、房间、机器人或其他资源定位方式是否接近 |
| GraphQL 资产 | Schema 获取、operation 生成、变量模板和 drift 能否适配 |
| 执行模型 | Locust-only 或 Locust + pytest/headless 是否符合目标 |
| 治理与报告 | catalog、主请求、阈值、workload 和报告是否确实需要 |

禁止复制参考仓库的 `.git`、`.venv`、缓存、真实 `.env`、报告、临时产物、账号映射或凭据。对源项目做选择性迁移，保留来源与适配说明；不要用目录名相似代替架构判断。

## 分阶段建立

### 阶段 1：项目契约

形成简短的 bootstrap 结论，至少列出：目标 endpoint/environment、首期场景、认证方式、Header/device 线索、Schema 来源、参考基线、暂缓项和未决风险。该结论可以先在对话中确认，不强制提前创建文档。

### 阶段 2：离线骨架

创建能运行静态验证的最小结构，通常包括依赖入口、Locust 入口、GraphQL client、统一 session/runtime state、profile loader、场景注册、测试和必要文档。只有目标需要时才引入 catalog、报告、容器与 CI；不要为了与大型参考仓库外观一致而复制全部能力。

运行时配置至少区分：

- 公共非敏感默认值；
- QA/UAT 等显式 profile；
- 不提交仓库的秘密或本机覆盖；
- endpoint override 与完整 profile 的不同语义。

示例 profile 可以保留结构和非敏感设备字段，但账号、token、Cookie 和 session 必须为空或通过安全外部来源注入。

### 阶段 3：Schema 与 operation 资产

取得真实环境授权和所需 profile 后，使用项目正式入口获取 live Schema，再生成 operation 与变量模板。只有客户端本地生成类型可用时，可把它作为临时契约线索建立离线骨架，但必须明确标记“未与 live Schema 核对”，且后续由 live 获取与 drift 检查替换或验证。

不要因为 introspection 成功就认为认证、业务查询或测试数据已准备完成。Schema 获取与业务请求验证是两个独立门槛。

### 阶段 4：首批场景

优先顺序通常是：

1. 无副作用的连通性或认证验活；
2. 认证链路及 session state；
3. 有稳定数据来源的只读查询；
4. 有恢复或清理策略的写操作；
5. 上传、删除、第三方登录等专用链路。

每个场景先定义主请求、前置请求、数据来源、失败口径和执行策略。OTP 请求、第三方登录、一次性 token 和 mutation 不应因“属于登录或测试”就默认视为无副作用。

### 阶段 5：验证升级

按能力逐层验证：

1. 文件结构、配置解析、单测、lint/typecheck；
2. 本地 Schema 解析、生成器和 drift；
3. 真实 Schema 同步；
4. 单用户、单 tag、短时 Locust 冒烟；
5. 报告主请求与失败分类；
6. 经明确授权的性能负载。

不得跳过前层问题直接用高并发验证。正式冒烟前确认 profile、账号容量、数据风险和是否存在会互踢的共享登录态。

## 新项目完成标准

交付必须按阶段说明状态：

- **已建立**：骨架、配置模型、GraphQL 资产管理、场景注册和测试入口实际存在且可运行；
- **已离线验证**：明确列出静态、单测、类型和本地契约结果；
- **已连接 live Schema**：说明环境和 profile，不泄露凭据；
- **已真实冒烟**：目标业务请求存在，Locust failure、GraphQL errors 与业务失败均符合预期；
- **未验证/阻塞**：账号、OTP、业务数据、权限或副作用授权缺失时单独列出。

“项目已创建”不等于“BFF 已验证”，“live Schema 可获取”也不等于“性能场景已就绪”。
